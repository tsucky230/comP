Give your AI a
map of your repository.

comP is a VS Code extension that indexes your repository's files, functions and call relationships on your own machine, and hands that index to AI coding agents such as Claude Code, Codex and Cursor. Ask comP at the start of a task, and the agent learns in one step where things live and what depends on what. It is open source, and the index and the work records stay on your machine.

I built it to cut token costs

The original goal was simple: make the AI read fewer tokens. Every time I asked Claude Code for a small fix, it ran grep after grep and opened files that had nothing to do with the task before it got anywhere. Paying for that exploration, in money and in waiting, on every request felt like a waste.

So I built a way to index the repository once and, given a description of the task, return only the files and symbols (names of functions and classes) that matter. Token use did go down. The longer I used it, though, the more I noticed a bigger change: the quality of the AI's work had changed.

An agent with a map more often opens the right file first, checks the callers before it changes a function, and picks up from the decisions of the last session. Its view widens from the file in front of it to the whole repository. I think that change is the most valuable thing comP does.

An AI with a map does better work

comP runs as an MCP server (MCP is the common protocol AI agents use to call outside tools). Normally you just ask for the work, and the agent calls comP's tools itself.

🧭

The right files on the first move

When the agent describes the task in one sentence to run_pipeline, it gets files ranked by relevance. Files with uncommitted changes come first, and files one dependency step away come along. Fewer detours through the wrong file, a wrong assumption and a restart.

🕸️

The blast radius before the change

get_impact_graph follows the dependency graph and lists every function and file that depends on a symbol. Called before an edit, it tells the agent which callers and tests to check. I want it to stop the slow decay in quality that builds up change after change.

📓

Yesterday's work and decisions, carried forward

What the agent looked up with run_pipeline and get_context is recorded across sessions automatically. When the agent saves the request and outcome with session_log, the decision is kept too, and the next session carries on with session_recall. Questions in Japanese work as well.

🔒

Your data stays put

The index and records live in the repository's .comp/. The daemon does not talk to any outside service, and the extension sends no telemetry. The one exception is @comp in VS Code chat, which sends your request and a compressed copy of attached files to the language model selected in VS Code.

comP's own development leans on the map too

When I asked for multi-root workspace support, the agent caught an existing bug from its first run_pipeline result, before writing any of the new feature. It read the returned daemon/src/main.rs and found that the additional_paths feature was wiping the main index. I think a map is what lets the agent see past the spot it was asked about.

The records survive a restart of the daemon (the background process that manages the index), and a switch from Claude Code to Codex loses nothing. In my experience, the memory features in Claude and ChatGPT are good at conversation summaries and preferences, while code details tend to drop out of those summaries. comP's records are an index of technical decisions in one repository. They remember different things, so I recommend using both.

Start in VS Code; agents are wired up for you

Press Start in the sidebar and a daemon written in Rust indexes the repository. Saved code and Markdown files are re-indexed on the spot, and a git branch switch rebuilds the whole index.

comP: Setup Agents writes to the configuration files that Claude Code, Codex, Cursor, Cline, Windsurf, Continue, GitHub Copilot, Antigravity, Aider and Gemini CLI actually read, keeping your other MCP servers. There is nothing to paste by hand. In VS Code chat, @comp also compresses attached files before they reach the LLM.

The numbers

How much comP helps depends heavily on the size of the repository and the kind of work. Here are the measurements I have, with their conditions.

📏

About 8,000 of about 440,000 tokens

What run_pipeline returned for the multi-root task in comP's own repository (9 files). It is compressed to fit the default budget of 8,000 tokens, about 1.8% of the whole repository. How much an agent would actually read depends on the task, so treat any saving computed from this as an upper bound.

🗺️

145,978 tokens, summarized in 289

One "get an overview" task in MAGATAMA's repository, measured on the MAGATAMA side: the estimated cost of reading selected source against a comP summary. A single measurement; other projects will not see the same ratio.

📦

Small repositories gain little

With a few dozen files, reading everything is cheap anyway, so there is less to gain (my expectation, not a measurement).

The effect a table misses: fewer do-overs

An agent that gets lost while exploring reads the wrong file, builds on a wrong assumption, fails the tests and starts over, and each round trip costs thousands of tokens (a rough estimate). In my own use, those round trips dropped noticeably once comP was in place, and the drop was largest with cheaper models.

With MAGATAMA, you get the places to check before a change, with evidence

MAGATAMA is a separate MCP server that reads comP's index and answers "if I change this file, what do I need to check?". comP draws the map; MAGATAMA uses it to inspect a change before you make it.

🔎

Which function to read first

Ask comP's run_pipeline and get_context.

🧩

What to check if this file changes

MAGATAMA's analyze_change_scope returns the candidates a change may ripple out to, with the dependency path to each as evidence.

🕰️

Why this file was changed last time

Search with MAGATAMA's history lookup and comP's session_recall.

🛰️

What has changed since the last session

Read the records of MAGATAMA's patrol (which checks changes made while you were away and keeps them for the next session) and comP's session_recall.

When it does not know, it says "unknown"

comP's get_impact_graph starts from one symbol and lists what depends on it. analyze_change_scope instead takes the files you plan to change, walks the dependencies backwards from every symbol in them, and attaches the path of impact to each candidate as evidence. When a file name is ambiguous, or the index lacks the dependencies to decide, analyze_change_scope answers "unknown (needs checking)" instead of guessing. I like that honesty. Treat the result as a starting point for review, not as proof of every runtime effect.

analyze_change_scope is not in the published PyPI release yet, so for now it is used from a MAGATAMA checkout that includes the feature. Setup steps are in MAGATAMA's README.

v0.1–v0.8.5

The index and the MCP server

Indexing with tree-sitter and an MCP server; indexing for Word, Excel, PowerPoint, PDF and Parquet; BM25 full-text search; automatic compression to a token budget; a rebuilt directory walk for large repositories.

v0.8.6–v0.9

Records that span sessions

session_log and session_recall keep requests and outcomes in .comp/history/ so the next session can find them. Since v0.9.4, comP repairs MCP settings on every start so an extension update never leaves them pointing at a stale path.

✅ Released
v0.10.0

Agent setup without copy and paste

Setup Agents writes straight into each agent's real configuration file, merged with your existing MCP servers.

✅ Released
v0.11.0–v0.11.6

Codex support, and sturdier data

Codex support, English/Japanese switching, re-indexing on branch switches, session records shared between agents, automatic recovery of a broken index or record, and exact token counts with tiktoken-rs.

✅ Released
v0.11.7–v0.11.8

Beta: conversation recording and rule sharing

Two features, off by default: automatic recording of Claude Code turns into .comp/history/, and returning the relevant sections of instruction files written for other agents. See Beta features.

✅ Released (beta)
v0.11.9–v0.11.11

Agent setting repairs and Antigravity 2.0

Codex's automatic review no longer rejects comP's tools, and stale paths left in Claude Code's registrations are fixed after an update. v0.11.11 supports Antigravity 2.0's settings file (~/.gemini/config/mcp_config.json) and removes the zstd vulnerabilities from the daemon.

✅ Released
v0.12.0

Multi-root workspaces

With several folders open in VS Code, an agent started in any folder can search all of them. Hidden folders directly under your home directory are refused by default, so a repository's settings file cannot read them. Deleting, moving or renaming a folder now reaches the index, and dependency edges and search results stay correct after re-indexing.

✅ Released

Getting started

Install it in VS Code, build the index, connect your agents. Three steps. comP needs VS Code 1.91 or later, and the daemon ships for Windows, macOS and Linux.

1

Install the extension

Search the VS Code Extensions view (Ctrl+Shift+X) for "comP - Code Context Engine" and install it. To install from a released .vsix file instead, run:

code --install-extension comP-0.12.1.vsix
2

Build the index

Open the repository you work on and press Start in the comP sidebar. The index is built in the background, and the status bar shows its progress. After the first run, only changed files are parsed again. The index and the work records go into the repository's .comp/, so add .comp/* and !.comp/ignore to .gitignore (committed as is, your work records and conversation text would reach the remote).

3

Connect your agents

Run comP: Setup Agents from the Command Palette and pick your agents. Agents found on this PC are already selected. Restart them afterwards (none of them re-read MCP settings while running). comP writes to:

  • Claude Code: .mcp.json (optionally also user scope via claude mcp add --scope user)
  • Codex: ~/.codex/config.toml and .codex/config.toml (the project file only takes effect for trusted projects)
  • GitHub Copilot: .vscode/mcp.json
  • Cursor: .cursor/mcp.json and ~/.cursor/mcp.json
  • Cline: the MCP settings in VS Code global storage
  • Windsurf: ~/.codeium/windsurf/mcp_config.json
  • Continue.dev: .continue/mcpServers/comp.yaml (project and home)
  • Antigravity (App, IDE, agy CLI, VS Code extension): ~/.gemini/config/mcp_config.json
  • Aider: .aider.conf.yml at the workspace root
  • Gemini CLI: .gemini/settings.json and ~/.gemini/settings.json (only with a paid Gemini API key or a Code Assist Standard / Enterprise license; personal accounts lost access on 2026-06-18)
